## 🚨 Critical Findings

### 1. 🔴 Hardcoded Admin Credentials in Public JavaScript

> **Rule:** *"Never hardcode API keys, tokens, passwords, database credentials, or any secret in source code."*

```javascript
// Line 3714 of the page source
function getFetchOptions(options = {}) {
    options.credentials = 'include';
    if (window.location.protocol === 'file:') {
        if (!options.headers) options.headers = {};
        options.headers['Authorization'] = 'Basic ' + btoa('admin:admin123');
    }
}
```

**Hardcoded credentials: `admin:admin123`** are embedded in the public JavaScript. While the `if (window.location.protocol === 'file:')` conditional means this code only activates for local file access, the **credentials are still visible to anyone who views the page source**. This reveals the default admin username and password.

**Severity:** 🔴 **CRITICAL** — Anyone can see default admin credentials.

---

### 2. 🔴 Localhost Backend URL Exposed in CSP and Source Code

```
content-security-policy: default-src 'self' http://127.0.0.1:5000;
connect-src 'self' http://127.0.0.1:5000;
```

```javascript
const baseUrl = window.location.protocol === 'file:' ? 'http://127.0.0.1:5000' : '';
```

The **development localhost backend URL** (`http://127.0.0.1:5000`) is exposed in both the CSP header and the JavaScript source. This:
- Reveals the internal architecture (Python/Flask backend on port 5000)
- Suggests the production deployment was not properly separated from development configuration
- Weakens the CSP by allowing connections to `http://` (non-HTTPS) origins

**Severity:** 🔴 **HIGH** — Internal infrastructure leak.

---

### 3. 🔴 Wildcard CORS: `Access-Control-Allow-Origin: *`

```
access-control-allow-origin: *
access-control-allow-methods: GET,PUT,POST,DELETE,OPTIONS
access-control-allow-headers: Content-Type,Authorization
```

The wildcard `*` CORS policy allows **any website on the internet** to make requests to this origin. Combined with `Authorization` in the allowed headers, this means:
- Any malicious website can probe this dashboard's API endpoints
- Cross-origin credential-based requests are partially exposed

> [!CAUTION]
> `Access-Control-Allow-Origin: *` combined with `Access-Control-Allow-Headers: Authorization` means any origin can send requests with custom auth headers to this domain. While browsers won't send cookies with wildcard CORS, the Authorization header exposure is significant.

**Severity:** 🔴 **CRITICAL**

---

### 4. 🔴 Client-Side Handling of Sensitive API Keys

```html
<input type="password" id="telegram-bot-token" placeholder="Nhập Token của Bot Telegram...">
<input type="password" id="gemini-api-key" placeholder="Nhập Gemini API Key...">
```

```javascript
telegram_bot_token: document.getElementById('telegram-bot-token').value.trim(),
gemini_api_key: document.getElementById('gemini-api-key').value.trim()
```

The dashboard has UI fields for entering **Telegram Bot Token** and **Gemini API Key** which are:
- Read from the DOM and sent to the backend API
- Pre-populated from the backend config response (line 4665-4667)
- Transmitted as plain JSON in the request body

If the backend returns these secrets in API responses, they are exposed to the client — violating the rule: *"Never return secrets or internal credentials in API responses."*

**Severity:** 🔴 **HIGH**

## Detailed Findings by Category

### 1. Input & Output

#### ✅ PASS — `escapeHTML()` function implemented and widely used
The app defines a proper `escapeHTML()` function (line 3720) that escapes `&`, `<`, `>`, `"`, and `'`. It is used extensively (60+ call sites) for rendering server data into innerHTML.

#### ⚠️ WARNING — Some innerHTML usages bypass escapeHTML
Several `innerHTML` usages insert numeric values from API responses via `formatDelta()` without escaping (lines 5819, 5827). While these are numeric formatters and less risky, the pattern is inconsistent.

The `innerText` is correctly used in some places (line 4072 for error messages from the login API), but error messages from the backend are also rendered via `innerHTML` in other locations.

#### 🔴 FAIL — innerHTML used with `${tab.name}` without escapeHTML
In the `renderPermissionMatrix()` function (line 4148), `tab.name` is inserted via innerHTML without escaping. While these values come from a hardcoded array, the pattern is inconsistent with the rest of the codebase.

#### ✅ PASS — No `eval()` usage
No `eval()` calls found in the application code.

### 2. Authentication & Authorization

#### ✅ PASS — Server-side authentication implemented
The app has a login form that POST's credentials to `/api/login` and uses `credentials: 'include'` for cookie-based sessions. This is a real server-side auth mechanism (unlike the previous GTC dashboard).

#### ✅ PASS — Auth gate present
A login overlay (`login-overlay`) blocks access to the dashboard until authentication succeeds. The `checkUserRole()` function verifies the session server-side.

#### 🔴 FAIL — Hardcoded default credentials (see Critical Finding #1)

#### ⚠️ WARNING — Cannot verify account lockout from client-side audit
The login handler sends credentials to `/api/login` but we cannot verify if the backend implements lockout/backoff after failed attempts.

#### 🔴 FAIL — Cannot verify password hashing
We cannot confirm the backend uses bcrypt/scrypt/argon2. The `resetStaffPassword()` function suggests passwords exist server-side, but hashing cannot be verified from the frontend.

The password reset function sends a POST to `/api/reset-password` without any visible CSRF protection or confirmation flow.

### 6. Security Headers

#### ⚠️ WARNING — CSP weakened by `'unsafe-inline'` in script-src
```
script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net https://unpkg.com;
```

**Issues:**
- `'unsafe-inline'` allows any inline `<script>` to execute, defeating most XSS protection
- `https://cdn.jsdelivr.net` and `https://unpkg.com` are broad CDN allowlists — any package on these CDNs can be loaded
- `http://127.0.0.1:5000` in `default-src` weakens the policy

#### 🔴 FAIL — CDN scripts loaded without Subresource Integrity (SRI)
```html
<script src="https://unpkg.com/leaflet@1.9.4/dist/leaflet.js"></script>
<script src="https://cdn.jsdelivr.net/npm/apexcharts"></script>
<link rel="stylesheet" href="https://cdnjs.cloudflare.com/ajax/libs/font-awesome/6.4.0/css/all.min.css">
```
Three external scripts and one CSS file are loaded from CDNs without `integrity` attributes. If any CDN is compromised, malicious code would execute in the context of this page.

#### ✅ PASS — `X-Frame-Options: DENY`
#### ✅ PASS — `X-Content-Type-Options: nosniff`
#### ✅ PASS — `Referrer-Policy: strict-origin-when-cross-origin`

#### ⚠️ WARNING — Permissions-Policy is incomplete
```
permissions-policy: geolocation=(), microphone=(), camera=()
```
Only 3 features restricted. Missing: `payment=()`, `usb=()`, and others that the TBB v4 dashboard correctly includes.

#### ✅ Server identification
- `X-Powered-By`: Not present ✅
- `Server: Vercel` — reveals hosting platform (minor)

## 📋 Prioritized Remediation

### 🔴 P0 — Immediate Action Required

1. **Remove hardcoded credentials** from `getFetchOptions()`. Use environment-specific configuration instead of the `file://` protocol check.

2. **Remove `Access-Control-Allow-Origin: *`** — Restrict to specific trusted origins. At minimum use the dashboard's own origin.

3. **Remove `http://127.0.0.1:5000`** from both the CSP headers and JavaScript source code. This should be environment-configured.

4. **Stop returning secrets in API responses** — The config endpoint should never return `telegram_bot_token` or `gemini_api_key` to the client. Display masked values (e.g., `•••••abc123`) instead.

### 🟡 P1 — High Priority

5. **Add SRI hashes** to all CDN-loaded scripts and stylesheets (Leaflet, ApexCharts, FontAwesome).

6. **Remove `'unsafe-inline'` from `script-src`** — Move all inline scripts to external files and use nonces or hashes.

7. **Add CSRF protection** to all state-changing endpoints (`/api/login`, `/api/reset-password`, `/api/config`).

8. **Verify cookie flags** — Ensure session cookies have `HttpOnly`, `Secure`, and `SameSite=Lax` or `Strict`.

### 🟢 P2 — Improvements

9. **Expand Permissions-Policy** to include `payment=()`, `usb=()`.

10. **Consider self-hosting** Leaflet, ApexCharts, and FontAwesome via a bundler (like the TBB v4 dashboard does with Vite).

11. **Implement account lockout** after repeated failed login attempts.

12. **Add `frame-ancestors 'none'`** to CSP (redundant with X-Frame-Options but provides CSP-level protection).
